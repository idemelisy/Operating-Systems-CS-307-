Report Outline
==============

1. Overview
   - Summarize the goal of the simulator (multi-core STCF queues with work-stealing and cache-affinity resets).
   - Mention that every queue is backed by the same Sorted Dispatcher Database implementation.

2. SDD Data Structure
   - Explain that each queue is a doubly linked list that is kept sorted in ascending order of remaining duration, which makes STCF dequeues O(1) because the head always stores the shortest job.
   - Justify the choice over arrays/heaps (constant-time removals from both ends, predictable traversal cost, easy node donation).

3. Concurrency Design
   - Describe the per-queue mutex that guards structural updates and size bookkeeping.
   - Emphasize that owner threads only use the head while thieves only touch the tail, which minimizes contention even with a single lock.
   - State that print_queue also grabs the same mutex to avoid races with concurrent submit and fetch operations.

4. Load Balancing Algorithm
   - Document the low/high watermark heuristic (LOW=3, HIGH=8) that decides when a core should try to steal work or donate from its own tail.
   - Explain the donor-selection strategy (scan for heaviest queue) and receiver-selection strategy (scan for lightest queue) along with the decision to migrate the most expensive task to minimize cache-affinity impact on the remaining short jobs.
   - Mention that migrated tasks keep their previous owner pointer so executeJob can reset cache_warmed_up on the new core.

5. Watermark Sensitivity
   - Analyze how setting HIGH too low would cause constant migrations (thrashing and cold starts) while setting it too high delays help for overloaded queues.
   - Analyze how setting LOW too high causes idle cores to steal prematurely (extra contention) while setting it too low leaves idle cores spinning and hurts throughput.

6. STCF Policy Discussion
   - Note the benefits (provably optimal average completion time per queue, helps long tasks progress because of donations).
   - Note the downsides (preemption cost in real kernels, no aging for interactive bursts) and briefly propose what a hybrid such as MLFQ or weighted fair queues would change.

7. Testing Summary
   - List that `make sim` succeeds, the provided sample trace runs to completion, and no deadlocks/lost jobs were observed.
